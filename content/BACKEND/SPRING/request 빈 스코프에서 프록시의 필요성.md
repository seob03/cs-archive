### 프록시가 없는 상태에서 문제가 발생하는 이유

여기서 request를 보자. request 스코프는 웹 요청이 “들어오고” 나갈 때까지 유지가 된다.

즉, 웹 요청이 들어와야 해당 스코프의 빈이 생성되게 된다. (매우 중요한 포인트)

만약에 프록시가 없게 되면 싱글톤이 시작할 때 request 스코프의 객체(예제에서는 `MyLogger` 클래스)를 바로 주입/생성하려고 하지만, 요청이 없으니 서버가 아예 뜨기 전에 터진다.

기존의 Controller나 Service는 싱글톤, 기본 스코프라 앱 시작할 때 바로 생성 및 주입이 되지만, request 스코프는 요청이 와야 주입이 가능하다는 차이가 있는 것이다.

### 프록시를 도입하면 어떻게 바뀌는가

![[스크린샷_2026-01-13_오후_10.38.56.png]]

처음에 싱글톤 주입하듯이 `MyLogger`의 프록시 객체를 그냥 싱글톤에 가짜 프록시 객체를 주입을 해 버린다.

물론 그 가짜 프록시 객체는 진짜 객체를 찾는 방법을 알고 있다.

클라이언트가 `myLogger.log()`을 호출하면 사실은 가짜 프록시 객체의 메서드를 호출한 것이다.

가짜 프록시 객체는 request 스코프의 진짜 `myLogger.log()`를 호출한다. 진짜 객체를 호출해도 이때는 이미 진짜 요청이 있었기 때문에 문제가 생기지 않게 된다. (프록시가 요청 시점에 진짜 request 빈으로 위임)

가짜 프록시 객체는 원본 클래스를 상속 받아서 만들어졌기 때문에 이 객체를 사용하는 클라이언트 입장에서는 원본이 아닌지도 모르게, 동일하게 사용할 수 있다.

즉, 프록시의 핵심은 **진짜 객체 조회를 꼭 필요한 시점까지 지연처리** 한다는 점이다.

즉, “미리 만들어야 해서 실패”가 “요청 때 찾아서 실행”으로 바뀌어서 동작하게 된다.

따라서 request 빈 스코프에서 프록시가 필요하게 되는 것이다.

==참고로 이미지를 보면 `@Scope("request")` 빈은 요청 1개당 1개 인스턴스가 원칙이기 때문에 클라이언트의 요청 별로 스프링 빈이 1개씩 생긴 것을 볼 수 있다. (기본 스코프인 싱글톤과 결과가 다른 것을 확인 가능함)==
